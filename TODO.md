- Capacity-aware ranking & candidate selection (DESIGN-SPEC, escalation-gated, REVIEW + VERIFY) — three problems now understood as one. (1) The board sorts by total profit but the headline is realizable, so card order does not match the headline once a ship capacity is entered; the displayed set should re-sort by realizable-given-capacity (client-side, since capacity is a client input and the current sort lives server-side in getTopRoutes — this forces a server/client ranking-boundary decision: server keeps fetch + shortlist + quarantine, client does the final capacity-aware sort). (2) Deeper finding 2026-05-31: the candidate set itself is capacity-blind. shortlistCommodities ranks the top-20 fetch set by global maxSell − minBuy with NO available-SCU and NO capacity awareness — it optimizes for a ship that can absorb unlimited supply (the competitor's fantasy-capacity failure mode, one layer up the pipeline). So the top-20 for a 696-SCU C2 are NOT the top-20 for a 35-SCU ship; better small-ship routes that never made the margin top-20 are never fetched and can never appear, no matter how the client sorts. Fixing this means a capacity-parameterized shortlist+fetch that re-runs when capacity changes — which touches UEX request fan-out (hygiene rules: bulk-first, per-commodity fan-out is the expensive path), so escalation-gated on two counts (ranking-input AND fan-out). (3) Also folds the original outlier-guard-v2 work: route count is a weak corroboration proxy (inflated by destination fan-out — live E'tam id 29 had 44 routes across only 3 origin terminals, realizable driven by scu_origin 67/22/7 not route count); the real trust signals are bottleneck SCU and distinct origin-terminal count. The shipped <=1 route-count guard is a first-pass stopgap (catches Osoian Hides only). Fix direction across all three: weight/filter the shortlist margin by available SCU (scu_buy / scu_sell_stock) AND by selected capacity; add bottleneck-SCU and origin-count trust signals; re-sort displayed routes (and routes within each card) by realizable. Unset capacity = ranks by total as today (realizable at infinite capacity equals total). Open question that triggered this (operator, 2026-05-31): "do the top-N even stay the top-N for a smaller ship?" — answer is no, which is why this is candidate-selection, not just a sort. Realizable-profit floor (separate Major bullet) is the natural partner. Verification: confirm the reorder matches hand-computed realizable at a test capacity, and that a known small-ship-favorable route enters the fetch set when capacity is small.
- Realizable-profit floor — a route/leg must clear a minimum realizable value (and a minimum bottleneck SCU) to be surfaced, so trivially-capped trades (the 6-SCU-Waste-in-a-Hull-E case) never rank. Directly motivated by the competitor anti-pattern. Ties to outlier guard v2 and (later) multi-leg routing. State-sensitive (changes what surfaces) — own evaluation.
- Loading/unloading fee as a net-profit term (DESIGN-SPEC, escalation-gated, MEASURE BEFORE BUILDING) — auto-loading commodities via the freight elevator has an associated aUEC fee that cuts into profit and is NOT currently modeled anywhere. UEX commodities_routes returns profit precomputed from buy/sell prices; it almost certainly does NOT account for a separate in-game loading fee, so the tool's displayed profit is likely OVERSTATED by the fee — and overstated more on large hauls if the fee scales per-SCU. This is a profit-math change (state-sensitive, escalation-gated) and a direct hit to the trust-critical number, so it must NOT be built on a guess. Blocking unknowns, all measurable in one real run: (a) does a distinct loading fee exist separate from the buy price, (b) is it flat per-transaction or per-SCU, (c) its magnitude. Resolve by observation — buy a load on a real run and compare credits deducted at the elevator against the raw buy price (see VERIFICATIONS calibration run). Once measured: subtract fee from realizable (realizable_profit − loading_fee, applied per leg; unload fee too if one exists), and feed the same fee into profit-per-hour and any future ROI/budget math. Until measured, displayed profit carries this known overstatement — note it as a disclaimer candidate on the profit surface. Pairs with the fuel-cost net-profit refinement (same family: real costs UEX's profit omits).
- Trade log / persistent user state (DESIGN-SPEC, own session) — operator-requested: a persistent record of runs made (commodity, route, ship, SCU, buy/sell, profit, timestamp). Significance beyond the feature: this is the FIRST capability requiring real persistence — everything today is in-memory (ship capacity included). It forces the parked storage decision (Vercel-only → Railway + DB backend) that lib/uex.ts was deliberately isolated to allow without touching handlers. Open questions: per-user identity (ties to any future auth/donation work), what a "run" record contains, manual entry vs inferred, whether logged real sell prices feed back into the price-override trust surface (a logged actual sale is a freshness signal). Pairs with user price overrides (shared storage need) and could seed personal analytics (your realized profit/hour over time — the honest version of the per-hour number).

- Risk / contested-route surface — define and surface "what you'll risk" on a route. ## Notes / Findings

- UEX Quantum Drives = category id 22 (section "Systems"). Quantum speed is the "Maximum Speed" attribute, unit km/s — sample 303,000 km/s for a size-1 grade-B civilian drive = ≈18.18 Gm/min, validating the QT_SPEED_GM_PER_MIN seed of 20 (close). Data is per-drive (Size/Grade/Class present), so per-ship QT is feasible later. NO spool/calibrate attribute exists in UEX data — SPOOL_CALIBRATE_MIN stays empirical (in-game measurement only). Confirmed via /api/verify-qt 2026-05-31.
- No official RSI commodity-market API exists or is planned (confirmed 2026-05); the game's per-shard/server-meshed economy makes one unlikely. UEX remains the best source.
- Supply/demand is player-influenced and tick-refreshed (5-15 min); feed quantities are fuzzy snapshots, not stable capacities. Reinforces staleness gating and overrides.
- Load/unload is a real per-SCU time cost (e.g. ~6-8 min for 696 SCU); belongs with travel-time constants for profit-per-hour.
- commodities_status endpoint rows decode status_origin/status_destination for display; commodities_prices_history available if route-count corroboration ever needs deepening.
- Architecture pivot: tool consumes commodities_routes rather than computing routes from commodities_prices_all. The v0.1 planRoutes ranker is being retired; its verification entry remains in VERIFICATIONS.md as historical record.
- ~~commodities_ranking endpoint is deprecated/disabled upstream~~ ❌ (struck through with error icon on the live UEX index, 2026-05-31) — not callable. Would not be used regardless: ranking stays in code for determinism (UEX score already struck as a trust signal). Do not look for it.
- Auto-loading / cargo box sizes (SCU container packing) — OUT OF SCOPE for ranking. Box composition affects load time and physical fit, not credits (profit is per-SCU regardless of packing); load time is already averaged into LOAD_UNLOAD_MIN_PER_SCU. The container_sizes field exists on commodities_prices_all if ever needed. Do not model box packing.
- Real-time accuracy ceiling — no official RSI market API exists; all tools (UEX included) work from crowd-sourced snapshots. Cannot beat UEX freshness via API. The only real-time edges are user price overrides (freshest source = the player at the terminal) and staleness gating on date_modified (honesty about age). Both already on backlog; this reinforces user price overrides as the top data-quality lever.
- Competitor reference (ohana-services, Base44, observed 2026-05-31) — full multi-leg wizard (region → ship → commodity/budget → AI route → review) with strong presentation but a broken engine: it scales buy quantities to ship capacity with NO supply check, producing impossible stops (e.g. BUY Compboard x188 where the terminal feed shows scu_buy 12; BUY Waste x6 where scu_buy is 1) and fantasy totals (Hull E "+3,995,220"). Verified against our prices feed: their buy prices are real, their quantities are not. This is the exact unbounded-capacity bug our three-way min + realizable-profit floor prevent. Borrow the flow (ship-first wizard, budget mode); do not borrow the engine. Note: read from screenshots + feed cross-check, not their source.
- Per-shard demand depletion (confirmed 2026-05-31) — terminal supply/demand is a shared, depleting pool per server shard, refreshing on 5–15 min ticks, not per-pilot reserved. Two traders on the same route draw down the same demand: the first sells into full demand, the second hits a lower price or a closed terminal. This is why single-run profit-per-hour overstates sustained earnings, and is the mechanical basis of the risk/contested-route surface. Physicalized-cargo load times (4.x): ~6–8 min for a C2's 696 SCU manually, 3–4 min with an ATLS mech — brackets the LOAD_UNLOAD_MIN_PER_SCU seed (0.01 ≈ 7 min/696) and confirms the auto-vs-manual split the constant comment flags.
- Product thesis (framing, 2026-05-31) — no official RSI market API exists or can realistically exist (per-shard, server-meshed economy; and trade friction IS the gameplay loop CIG is designing, so they have no incentive to remove it). The missing API is therefore structural and permanent, not a temporary gap. This is freeing: the tool is not a worse version of an API that should exist — it is the thing that is only valuable BECAUSE the API cannot exist. Every hard problem (staleness, contention, freshness, overrides) shares one root — no ground truth — and that root is also the moat. UEX, Datarunner, and this tool compete on how well they cope with not knowing, not on data access. North-star statement: the freshest, most honest read on an economy nobody can see directly.
- Load/unload time model — auto-load only (operator's confirmed workflow: cargo elevator / auto-load, no hand-stacking, no ATLS, no crew). This simplifies the time model and justifies keeping the per-SCU term linear (auto-load throughput is roughly constant per SCU; it was manual/crew loading that broke linearity). Honest model is FIXED_LOAD_MIN + LOAD_UNLOAD_MIN_PER_SCU × scu: a fixed overhead per stop (dock → get to terminal → take off, roughly constant) plus a linear auto-load term. The current model has only the linear term (LOAD_UNLOAD_MIN_PER_SCU × scu_origin) with no fixed floor, so it UNDERESTIMATES small loads — structurally wrong below ~50 SCU, i.e. exactly the operator's Avenger Titan (8 SCU) regime. Boundary caution: a fixed load overhead may overlap the existing TERMINAL_OVERHEAD_MIN (landing + ASOP + walk-to-terminal) — define each constant's scope at calibration time to avoid double-counting the fixed term. This is the concrete motivation for the Range-model-v2 / per-constant split already in Minor: split the load constant into fixed + scalar. Avenger Titan corrected to 8 SCU (earlier note of 46 was wrong).
